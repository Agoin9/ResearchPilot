| 项目 | 内容 |
| --- | --- |
| 产品名称 | ResearchPilot 研途智控 |
| 文档版本 | v1.0（MVP 方案，待确认） |

| 技术栈（固定） | 前端 React + TypeScript + Vite + Tailwind CSS + shadcn/ui + Recharts；后端 Python FastAPI + SQLite；AI 推理全部交给 DeepSeek API（deepseek-chat） |

## 1. 产品概述

ResearchPilot 是一款面向研究生的科研任务智能管理 Web 应用。

研究生输入**科研目标、截止时间、每周可用时间**，系统自动调用 DeepSeek 大模型将大目标拆解为可执行的任务看板；日常记录任务完成进度，系统自动识别延期风险，并在需要时调用 DeepSeek 生成重规划方案，帮助研究生告别拖延、按时完成科研目标。

**一句话定位**：研究生的"科研导航员"——把大目标拆成小任务，延期了自动帮你重新规划。

**核心原则**：AI 是"增强功能"，不是"必需功能"。断网、没有 API Key、AI 调用失败时，任务管理、进度记录、风险识别等核心功能必须照常可用。

## 2. 目标用户与产品痛点

### 2.1 目标用户

| 用户画像 | 特征 |
| --- | --- |
| 硕士 / 博士研究生 | 有明确科研产出要求：开题、文献综述、实验、小论文、大论文、答辩 |
| 科研周期长 | 单个目标持续 3 个月 ~ 3 年，目标遥远、缺乏中间节点 |
| 时间碎片化 | 每周可用时间有限（约 5~20 小时），还需兼顾课程、助教、实习 |
| 有拖延倾向 | 缺乏进度监督和及时反馈机制 |
| 非技术背景偏多 | 不擅长复杂的项目管理工具，需要"傻瓜式"体验 |

### 2.2 核心痛点

| # | 痛点 | 现状 | ResearchPilot 的解法 |
| --- | --- | --- | --- |
| 1 | 拆解难 | 导师只给大目标（"年底前完成论文初稿"），不知道如何拆成每天能干的事 | AI 自动拆解为里程碑 + 具体任务 |
| 2 | 计划难 | 手工排期繁琐，不会估算任务耗时 | AI 依据截止时间 + 每周可用时间自动排期 |
| 3 | 发现晚 | 任务延期后知后觉，临近截止才发现来不及 | 规则引擎实时识别延期风险并醒目提示 |
| 4 | 调整难 | 延期后不知如何重排优先级，往往直接放弃 | AI 结合全局进度生成重规划方案，一键采纳 |
| 5 | 无监督 | 没有进度反馈，动力不足 | 进度记录 + 可视化图表反馈 |

### 2.3 与现有工具的区别

- 通用项目管理工具（Trello / Notion / 飞书）：功能通用，但**不会针对科研目标做 AI 拆解**，**没有延期自动重规划**。
- 论文写作工具：只管写作环节，不管开题、实验、答辩等全过程。
- 手工 Excel：更新成本高，无风险预警，无图表反馈。

## 3. 完整用户使用流程

### 3.1 首次使用（主线流程）

1. 打开应用 → 进入**仪表盘**（空状态，引导"创建第一个项目"）。
2. 点击"新建项目"→ 填写表单：
   - 项目名称（如"毕业论文"）
   - 科研目标描述（如"2026 年 12 月底前完成毕业论文初稿，包含文献综述、实验设计和数据分析"）
   - 截止时间
   - 每周可用小时数（如 15 小时）
3. 点击"**AI 智能拆解**"→ 后端调用 DeepSeek → 返回任务拆解**预览**（里程碑 + 任务 + 建议起止日期 + 预计耗时）。
4. 用户在预览中可增、删、改任务 → 点击"**确认创建**" → 任务批量写入看板。
5. 自动跳转到项目看板，开始执行。

> 说明：若 DeepSeek 不可用，第 3 步降级为"跳过拆解，进入空看板手动添加任务"。

### 3.2 日常使用流程

1. 打开应用 → 仪表盘查看：项目概览卡片、延期风险提醒、任务完成趋势图。
2. 进入项目看板 → 查看三列任务：待开始 / 进行中 / 已完成。
3. 开始任务：点击"开始"→ 任务状态变为"进行中"。
4. 推进任务：点击"更新进度"→ 填写：
   - 进度百分比（滑动条 0~100）
   - 本次投入小时数（可选）
   - 备注：做了什么、卡在哪里（可选）
   - 提交后写入**进度记录**（用于图表和时间线）。
5. 完成任务：进度 100%，任务自动进入"已完成"列。
6. 查看图表：仪表盘查看近 30 天完成趋势、任务状态分布、实际投入 vs 计划投入。

### 3.3 风险识别与重规划流程

1. 系统在每次读取数据时，用**本地规则引擎**（见 §9，不消耗 AI）自动计算风险：
   - 🔴 高风险：任务已逾期未完成
   - 🟡 中风险：进度落后于计划超过阈值
2. 仪表盘、项目看板醒目展示风险标记。
3. 用户点击"**AI 重规划**"（手动触发，或看到风险提示后触发）→ 后端把当前全部任务与进度交给 DeepSeek → 返回重规划方案（文字说明 + 结构化调整建议）。
4. 用户查看方案弹窗：
   - 点击"**采纳**" → 调整自动应用到任务（改起止日期、优先级等）→ 方案存入历史，状态=已采纳
   - 点击"**放弃**" → 不应用，方案存入历史，状态=已放弃
5. 重规划历史可随时回看。

### 3.4 流程总览（文字流程图）

```
┌─────────────┐   ┌──────────────────┐   ┌──────────────┐
│  新建项目     │ → │  AI 拆解（预览确认） │ → │   任务看板     │
│ 目标/截止/时间 │   │  可增删改后写入     │   │ 三列:待做/进行/完成│
└─────────────┘   └──────────────────┘   └──────┬───────┘
                                                 │ 日常更新进度
                                                 ▼
                      ┌──────────────────────────────────────┐
                      │  风险引擎（本地规则，自动运行）           │
                      │  逾期→高风险 / 进度落后→中风险           │
                      └──────────────────┬───────────────────┘
                                         │ 有风险
                                         ▼
                      ┌──────────────────────────────────────┐
                      │  AI 重规划 → 预览方案 → 采纳/放弃        │
                      │  采纳后自动调整任务，历史留档             │
                      └──────────────────────────────────────┘
```

## 4. 系统架构

### 4.1 整体架构图（文字描述）

```
┌──────────────────────────────────────────────┐
│  浏览器（用户）                                │
│  React + TypeScript + Vite                    │
│  界面：Tailwind CSS + shadcn/ui               │
│  图表：Recharts                               │
│  路由：react-router-dom                       │
│  请求：axios（统一封装）                       │
└────────────────────┬─────────────────────────┘
                     │ HTTP / JSON（RESTful API）
                     ▼
┌──────────────────────────────────────────────┐
│  后端服务 Python FastAPI                      │
│  ├─ 路由层 routers/：项目、任务、进度、AI、统计  │
│  ├─ 业务层 services/：拆解编排、风险计算、      │
│  │   重规划编排、统计分析                      │
│  ├─ 风险识别引擎（纯本地规则，不调 AI）         │
│  ├─ AI 客户端 ai_client/：调用 DeepSeek，      │
│  │   含 Prompt 组装、JSON 解析、重试、降级     │
│  └─ 数据层 SQLAlchemy ORM + Pydantic 校验     │
└──────────┬───────────────────────┬───────────┘
           │ SQLAlchemy            │ HTTPS
           ▼                       ▼
┌──────────────────┐   ┌──────────────────────────┐
│ SQLite 本地数据库 │   │ DeepSeek API              │
│ research.db      │   │ POST https://api.deepseek │
│                  │   │ .com/v1/chat/completions  │
│                  │   │ model: deepseek-chat      │
└──────────────────┘   └──────────────────────────┘
```

**关键设计说明**：

1. **前端绝不直接调用 DeepSeek**。API Key 只保存在后端 `.env` 文件中，不进 git、不出现在浏览器。
2. AI 调用采用"请求-响应"同步模式（MVP 简化，不做流式输出），前端显示 loading 动画。
3. **风险识别是纯本地规则计算**，不消耗 AI token，每次读数据实时计算、不落库。
4. 前端状态管理 MVP 使用 React 内置状态（useState/useEffect）+ 操作后重新请求刷新，**不引入 Redux** 等重状态库，降低复杂度。

### 4.2 模块划分

**前端模块**：

| 模块 | 职责 | 主要技术 |
| --- | --- | --- |
| API 封装层 | 统一 axios 实例、baseURL、错误统一提示（toast） | axios |
| 路由层 | 页面跳转、页面级懒加载 | react-router-dom |
| 布局组件 | 侧边栏（导航）+ 顶栏（面包屑/快捷入口） | shadcn/ui |
| 页面组件 | 仪表盘、项目列表、新建向导、项目看板、任务弹窗、重规划弹窗 | shadcn/ui |
| 图表组件 | 趋势图、状态分布图、时间投入图 | Recharts |
| 通用组件 | 风险标记、进度条、空状态引导、Loading | shadcn/ui + 自研 |

**后端模块**：

| 模块 | 职责 |
| --- | --- |
| config | 读取配置：DeepSeek Key、数据库路径、风险阈值（.env） |
| models | SQLAlchemy 表模型：project / task / progress_record / replan_history |
| schemas | Pydantic 请求/响应模型（输入校验 + 输出序列化） |
| routers | 路由：projects / tasks / ai / stats |
| services | 业务逻辑：任务拆解编排、风险计算、重规划编排、统计分析 |
| ai_client | DeepSeek 调用封装：Prompt 模板、JSON 输出约束、解析校验、失败重试、降级 |
| main | FastAPI 应用入口：CORS、路由注册、启动建表 |

### 4.3 数据流

**① 普通读数据流**
```
用户打开页面 → 前端 GET 请求 → FastAPI 路由 → 业务层（顺带计算风险）
→ ORM 查 SQLite → Pydantic 序列化 → 返回 JSON → 前端渲染
```

**② 普通写数据流**
```
用户操作（创建项目/更新任务/记录进度）→ POST/PUT 请求 → Pydantic 校验
→ 写 SQLite → 返回最新数据 → 前端刷新界面
```

**③ AI 拆解数据流**
```
前端点"AI 拆解" → POST /decompose → 后端组装 Prompt（目标+截止+每周时间+当前日期）
→ 调用 DeepSeek → 返回 JSON 文本 → 后端解析 + Pydantic 校验（失败重试 1 次，仍失败则降级）
→ 返回任务 draft（不写库）→ 前端展示预览，用户增删改
→ POST /decompose/confirm → 批量写 task 表 → 跳转看板
```

**④ AI 重规划数据流**
```
前端点"AI 重规划" → POST /replan → 后端取项目+全部任务+进度+风险任务
→ 组装 Prompt → DeepSeek → 解析出（文字方案 + 结构化变更）
→ 写 replan_history 表（status=pending）→ 返回方案给前端展示
→ 用户点"采纳" → POST /adopt → 应用变更到 task 表 → status=adopted
```

**⑤ 风险识别数据流**
```
读取项目列表/详情时 → 后端风险引擎实时计算每个任务和项目的风险等级
（纯本地规则，查表即可，不存储）→ 随响应 JSON 一起返回 → 前端渲染风险标记
```

## 5. 数据库表结构（SQLite）

共 4 张表，关系：`project 1─N task 1─N progress_record`，`project 1─N replan_history`，`task 自关联（parent_id）`。

### 5.1 project 项目表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | 主键，自增 | 项目 ID |
| name | TEXT | 非空 | 项目名称，如"毕业论文" |
| goal | TEXT | 非空 | 科研目标描述（AI 拆解的输入素材） |
| deadline | DATE | 非空 | 项目截止日期 |
| weekly_hours | REAL | 非空，>0 | 每周可用小时数（AI 排期依据） |
| status | TEXT | 默认 active | active 进行中 / completed 已完成 / paused 已暂停 |
| created_at | DATETIME | 自动 | 创建时间 |
| updated_at | DATETIME | 自动 | 更新时间 |

### 5.2 task 任务表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | 主键，自增 | 任务 ID |
| project_id | INTEGER | 外键 → project.id，级联删除 | 所属项目 |
| parent_id | INTEGER | 外键 → task.id，可空，级联删除 | 父任务（里程碑）；NULL 表示自己是里程碑 |
| title | TEXT | 非空 | 任务标题 |
| description | TEXT | 可空 | 任务描述 |
| status | TEXT | 默认 todo | todo 待开始 / doing 进行中 / done 已完成 |
| priority | TEXT | 默认 medium | high 高 / medium 中 / low 低 |
| planned_start_date | DATE | 可空 | 计划开始日期 |
| planned_end_date | DATE | 可空 | 计划截止日期 |
| estimated_hours | REAL | 可空 | 预计耗时（AI 依据每周可用时间估算） |
| progress | INTEGER | 默认 0，0~100 | 完成进度百分比 |
| is_milestone | BOOLEAN | 默认 false | 是否里程碑节点 |
| sort_order | INTEGER | 默认 0 | 同组内排序序号 |
| created_at | DATETIME | 自动 | 创建时间 |
| updated_at | DATETIME | 自动 | 更新时间 |

> 层级约定：**两级结构**。里程碑（parent_id 为空、is_milestone=true）下挂普通任务。MVP 不做任意层级嵌套。

### 5.3 progress_record 进度记录表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | 主键，自增 | 记录 ID |
| task_id | INTEGER | 外键 → task.id，级联删除 | 所属任务 |
| progress | INTEGER | 非空，0~100 | 本次更新后的累计进度 |
| hours_spent | REAL | 可空，≥0 | 本次投入小时数 |
| note | TEXT | 可空 | 备注（做了什么 / 卡在哪） |
| created_at | DATETIME | 自动 | 记录时间（图表 X 轴、时间线排序依据） |

> 每次用户更新进度都会写一条记录，任务表 task.progress 同步更新为最新值。历史记录永不删除，用于绘制"进度随时间变化"曲线。

### 5.4 replan_history 重规划历史记录表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | 主键，自增 | 方案 ID |
| project_id | INTEGER | 外键 → project.id，级联删除 | 所属项目 |
| trigger_type | TEXT | 非空 | manual 用户手动 / risk 风险提示触发 |
| risk_tasks_json | TEXT(JSON) | 可空 | 触发时的风险任务快照（标题/进度/截止等） |
| plan_content | TEXT | 非空 | DeepSeek 返回的方案正文（给用户看的文字） |
| changes_json | TEXT(JSON) | 可空 | 结构化变更列表（采纳时逐条应用到 task 表） |
| status | TEXT | 默认 pending | pending 待处理 / adopted 已采纳 / rejected 已放弃 |
| created_at | DATETIME | 自动 | 生成时间 |
| decided_at | DATETIME | 可空 | 采纳/放弃时间 |

## 6. 前端页面清单

| # | 页面 | 路由 | 核心功能 |
| --- | --- | --- | --- |
| 1 | **仪表盘** | `/` | ① 项目概览卡片（名称、总进度、剩余天数、风险等级）；② 风险提醒区（列出所有风险任务，点击跳转对应看板）；③ 任务完成趋势图（近 30 天完成的进度记录/完成任务数，Recharts 柱状或折线）；④ 任务状态分布饼图（待做/进行/完成）；⑤ 时间投入统计（实际投入 vs 计划投入）；⑥ 空状态引导（无项目时引导创建） |
| 2 | **项目列表** | `/projects` | ① 全部项目卡片（进度条、风险标记、剩余天数、截止日期）；② "新建项目"入口；③ 卡片点击进入看板；④ 项目编辑/删除入口 |
| 3 | **新建项目向导** | `/projects/new` | ① 表单：名称、科研目标、截止时间（日期选择器）、每周可用小时（数字输入）；② "AI 智能拆解"按钮 → loading 动画 → 展示拆解预览；③ 预览区：里程碑/任务两级列表，可增、删、改（标题/日期/优先级）；④ "确认创建" → 写入看板并跳转；⑤ "跳过，手动创建"降级入口 |
| 4 | **项目详情（看板）** | `/projects/:id` | ① 顶部项目信息卡（目标、截止倒计时、每周时间）+ 编辑按钮；② 风险横幅（有高风险时红色醒目提示 + "AI 重规划"快捷按钮）；③ 三列看板：待开始 / 进行中 / 已完成，任务卡片显示标题、优先级、截止、进度条、风险标记；④ 卡片操作按钮：开始 / 更新进度 / 完成 / 编辑 / 删除；⑤ "手动添加任务"（可直接在列中添加）；⑥ "AI 重规划"按钮；⑦ "重规划历史"入口 |
| 5 | **任务详情弹窗** | 看板内弹窗 | ① 查看/编辑任务信息（标题、描述、起止日期、优先级、预计耗时）；② 进度更新区：滑动条（0~100）+ 本次投入小时 + 备注 → 提交生成进度记录；③ 进度历史时间线（每次记录的时间、进度、备注）；④ 一键"标记完成" |
| 6 | **重规划方案弹窗** | 项目内弹窗 | ① 展示 AI 方案文字说明；② 展示结构化变更预览（哪些任务改日期/优先级/建议删减，逐条列出）；③ 按钮："采纳方案"（应用变更）/"放弃"；④ 应用成功后看板自动刷新 |
| 7 | **重规划历史** | 项目内抽屉/页面 | ① 历史方案列表（时间、触发原因、状态徽章）；② 点击查看方案全文与变更内容；③ 未处理的方案可在此重新采纳/放弃 |
| 8 | **项目统计页** | `/projects/:id/stats` | ① 各任务进度历史折线图（基于进度记录）；② 里程碑完成情况；③ 实际 vs 计划时间投入对比图（Recharts 柱状图） |

**看板交互说明**：MVP 用**按钮操作**（开始/完成/更新进度），不实现鼠标拖拽（拖拽列为后期增强项，降低 MVP 复杂度）。

## 7. API 接口清单（后端提供给前端）

统一前缀 `/api`，请求/响应均为 JSON；错误统一返回 `{"detail": "错误说明"}` 及相应 HTTP 状态码。

### 7.1 项目类

| 方法 | 路径 | 说明 | 请求体要点 | 响应要点 |
| --- | --- | --- | --- | --- |
| POST | `/api/projects` | 创建项目 | name, goal, deadline, weekly_hours | 项目对象 |
| GET | `/api/projects` | 项目列表 | 无 | 项目数组（含总进度、风险等级、任务数） |
| GET | `/api/projects/{id}` | 项目详情 | 无 | 项目 + 任务树（含每个任务的风险标记）+ 项目风险等级 |
| PUT | `/api/projects/{id}` | 更新项目 | name/goal/deadline/weekly_hours/status | 更新后的项目 |
| DELETE | `/api/projects/{id}` | 删除项目（级联删除任务、进度、重规划历史） | 无 | 204 |
| GET | `/api/projects/{id}/stats` | 项目统计数据（统计页图表用） | 无 | 各任务进度历史、里程碑完成情况、实际 vs 计划投入 |

### 7.2 任务类

| 方法 | 路径 | 说明 | 请求体要点 | 响应要点 |
| --- | --- | --- | --- | --- |
| POST | `/api/tasks` | 手动创建任务 | project_id, title, description?, parent_id?, priority?, planned_start_date?, planned_end_date?, estimated_hours? | 任务对象 |
| PUT | `/api/tasks/{id}` | 更新任务（改状态/日期/优先级/标题等） | 任意待更新字段 | 更新后的任务 |
| DELETE | `/api/tasks/{id}` | 删除任务（级联删除其进度记录和子任务） | 无 | 204 |
| POST | `/api/tasks/{id}/progress` | 新增进度记录 | progress(0~100), hours_spent?, note? | 新记录 + 更新后的任务 |
| GET | `/api/tasks/{id}/progress` | 进度记录列表（时间升序） | 无 | 记录数组 |

### 7.3 AI 类（DeepSeek）

| 方法 | 路径 | 说明 | 请求体要点 | 响应要点 |
| --- | --- | --- | --- | --- |
| POST | `/api/projects/{id}/decompose` | AI 拆解任务（**不写库**，返回草稿） | 可选覆盖参数 | draft：里程碑+任务数组（含建议起止日期、预计耗时） |
| POST | `/api/projects/{id}/decompose/confirm` | 确认拆解结果（用户可能在预览中改过） | 任务数组 | 写入后的任务树 |
| POST | `/api/projects/{id}/replan` | AI 重规划 | 无（后端自动收集当前任务与风险） | 方案对象：plan_content 文字 + changes 结构化变更 + 方案 id |
| GET | `/api/projects/{id}/replans` | 重规划历史列表 | 无 | 方案数组（不含过长内容，详情单查或前端已有） |
| POST | `/api/replans/{id}/adopt` | 采纳方案（应用变更到任务） | 无 | 应用结果摘要 |
| POST | `/api/replans/{id}/reject` | 放弃方案 | 无 | 更新后的方案对象 |

### 7.4 风险识别说明

**风险不设独立接口**：后端在 `GET /api/projects`（列表）和 `GET /api/projects/{id}`（详情）响应中，为每个任务附带 `risk` 字段（none / medium / high）和风险原因，为项目附带项目级风险等级，前端直接渲染。这样用户每次打开页面看到的都是最新风险，且零额外请求。

## 8. AI 集成设计（DeepSeek）

### 8.1 调用方式

- 调用方：**后端 ai_client 模块**，前端不直接接触 API Key。
- 接口：`POST https://api.deepseek.com/v1/chat/completions`
- 模型：`deepseek-chat`
- 温度：拆解 `0.3`（求稳定），重规划 `0.4`
- 超时：60 秒；前端全程显示 loading 动画。
- API Key：存放于后端 `.env` 文件，`.gitignore` 排除，提供 `.env.example` 模板。

### 8.2 输出稳定性保障（重点）

1. **强约束 Prompt**：明确要求"只输出 JSON，不要任何解释文字"，并给出完整的 JSON 格式示例。
2. **后端解析 + 校验**：收到文本后解析 JSON，再用 Pydantic 模型逐字段校验（类型、枚举值、日期格式）。
3. **失败重试**：解析/校验失败自动重试 1 次（附"上次输出格式不对"的纠错说明）。
4. **降级兜底**：仍失败时返回友好错误提示，引导用户手动创建任务，**应用不崩溃**。

### 8.3 拆解 Prompt 输入/输出

- 输入：科研目标描述、项目截止日期、每周可用小时数、当前日期。
- 输出（JSON）：2~4 个里程碑，每个里程碑下 3~6 个任务；每个任务含：标题、描述、预计耗时（小时）、建议起止日期、优先级。日期必须落在项目截止日期之前，总耗时与每周可用时间匹配（后端校验）。

### 8.4 重规划 Prompt 输入/输出

- 输入：项目信息、全部任务及其进度、风险任务列表（哪些逾期/落后）。
- 输出（JSON）：① `plan_content` 文字方案（给用户看的分析说明）；② `changes` 结构化变更列表，每项含：task_id、变更类型（改起止日期 / 改优先级 / 建议删减 / 建议拆分）、新值、理由。

## 9. 风险识别规则（本地规则引擎，不调 AI）

| 级别 | 规则 | 说明 |
| --- | --- | --- |
| 🔴 高风险 | 任务未完成（status ≠ done）且 `planned_end_date` < 今天 | 已逾期 |
| 🟡 中风险 | 计划时间已过 > 30%，且实际进度落后于"应达进度"超过 20 个百分点 | 进度落后 |
| ⚪ 无风险 | 其余情况（含未到开始时间、已完成、正常推进） | — |

- 应达进度计算公式：`应达进度 = 已过天数 ÷ 计划总天数 × 100`（任务没有计划起止日期时不参与进度落后判断）。
- 项目级风险汇总：任一任务高风险 → 项目高风险；≥3 个任务中风险，或项目整体进度落后 20% → 项目中风险。
- 所有阈值（30%、20 个百分点等）集中在后端配置常量中，可随时调整；前端展示风险原因，让用户理解"为什么提示风险"。

## 11. 验收标准

**总体验收（M8 完成后必过）**：

1. 端到端主流程可跑通：新建项目 → AI 拆解（预览可增删改）→ 确认写入看板 → 开始/更新进度/完成任务 → 逾期或落后出现风险提示 → AI 重规划 → 采纳后任务自动调整 → 历史可查。
2. 数据持久化：重启前后端后数据完整保留。
3. 核心功能不依赖 AI：不配置 API Key 或断网时，除 AI 拆解/重规划外全部功能正常，AI 功能给出友好错误提示（不崩溃、不白屏）。
4. 风险提示准确：人为构造逾期任务 → 显示高风险；构造进度落后任务 → 显示中风险。

**分阶段验收**：

| 阶段 | 验收标准 |
| --- | --- |
| M1 | 一条命令启动前后端；浏览器访问前端，`/api/health` 返回 ok |
| M2 | FastAPI 自带 /docs 页面可对 4 张表全部接口完成增删改查，数据落库 |
| M3 | 所有页面路由可导航；接口返回错误时前端有 toast 提示 |
| M4 | 不靠 AI 走通：建项目 → 手动加任务 → 看板三列流转 → 编辑删除 |
| M5 | 更新进度写记录；仪表盘图表随真实数据变化 |
| M6 | 人为构造逾期/落后任务，前端出现对应红色/黄色风险标记，原因可读 |
| M7 | 配置 Key 后 AI 拆解成功率 ≥ 80%（同一目标测 5 次）；重规划方案可采纳并正确修改任务 |
| M8 | 全部总体验收项通过，无阻塞性 bug |

## 12. 潜在风险与应对

| # | 风险 | 影响 | 应对策略 |
| --- | --- | --- | --- |
| 1 | DeepSeek 返回格式不稳定 | AI 结果解析失败、体验差 | 强约束 Prompt + Pydantic 校验 + 重试 1 次 + 降级手动模式（§8.2） |
| 2 | API 不可用 / 欠费 / 超时 | AI 功能不可用 | 核心功能与 AI 解耦，AI 仅增强；错误提示友好，引导手动操作 |
| 3 | 用户环境配置困难（Windows + 编程小白） | 应用跑不起来 | README 提供傻瓜式步骤（装 Python/Node → 配置 Key → 启动）；提供 .env.example 模板 |
| 4 | AI 拆解质量不佳 | 任务不合理、用户不信任 | "预览-确认"模式允许用户自由增删改后再写入 |
| 5 | 风险阈值不准确 | 误报（狼来了）或漏报 | 阈值集中为配置常量，可调；前端展示风险原因，透明可信 |
| 6 | SQLite 并发写入限制 | 多用户同时写冲突 | MVP 为本地单用户，足够；后期多用户再迁移 PostgreSQL |
| 7 | 范围蔓延 | 工期失控 | MVP 明确砍掉：登录注册、拖拽看板、消息通知、多用户（列入后期规划 §14） |
| 8 | Windows 路径/编码问题 | 中文乱码、路径报错 | 统一 UTF-8；路径处理用 Python pathlib；README 针对 Windows 说明 |

## 13. MVP 范围决策（需用户确认）

| # | 决策 | 说明 | 理由 |
| --- | --- | --- | --- |
| 1 | **单用户本地使用，不做登录注册** | 数据存本机 SQLite | 研究生个人工具，省去账号体系复杂度，后期可加 |
| 2 | AI 拆解"预览-确认"两步 | 先看草稿，改完再写入 | 兼顾 AI 效率与人工可控 |
| 3 | 任务两级结构（里程碑+任务） | 不嵌套更多层级 | 科研场景够用，看板清晰 |
| 4 | 风险识别用本地规则引擎 | 不消耗 AI token | 免费、即时、可解释 |
| 5 | 看板用按钮操作，不做拖拽 | 开始/完成/更新进度用按钮 | 降低 MVP 复杂度，拖拽列入后期 |
| 6 | 不做站外通知（邮件/推送） | 打开应用时看风险提醒 | 本地应用无服务端，后期可加 |
